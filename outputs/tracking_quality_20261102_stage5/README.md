# F1/F2入れ替わりの指摘への対応（2026-11-02）

ユーザーから、第4段階の途中初期化・再取得でF1/F2が入れ替わると指摘された。
第4段階は本人対応に失敗を含む版として保持し、READMEと
`../tracking_quality_20261102_stage4/HUMAN_FEEDBACK_ID_SWITCH.md`へ記録した。
発言から正確な全フレーム・各接続の正誤までは確定できないため、一括反転や
個別の接続すべてへの人手正誤ラベルの付与はしていない。

## 問題

再取得候補は、主に見失っている人物の間で比較していた。
相方が現在追跡中なら、相方にも同じ程度に似た候補でも大きな割り当て余裕が出得る。
8フレーム連続することは候補の持続の確認であり、本人一致の証明にはならない。
またF1/F2は各区間の初期位置から付けた仮ラベルで、試合全体の選手名との対応ではない。

## 今回の処理

1. 引き継ぎ先を、現在追跡中の相方も含めて比較する。初期の特徴は固定して保持する。
2. 初期の服の特徴が似るペアでは、長い欠落後に自動で元IDを復元しない。
   短い元ID変更でも、自分の位置予測が近く相方の予測と離れている条件を要求する。
3. 条件を満たさない引き継ぎは、状態・服特徴の更新も取り消し、成功イベントとして残さない。
4. 未割り当ての奥側の人物らしい検出を灰色の **F?** で別表示する。
   F?はF1/F2のどちらかを確定した印ではなく、選手でない誤検出が残る可能性もある。
   CSVのperson slotは空欄、identity_statusはunresolved。

服特徴の差の閾値は開発用の経験的な設定であり、独立した性能検証はしていない。
色で区別できないペアの正しい本人再識別は未解決。今回改善したのは、識別不能な候補に
本人IDを強制して連続追跡として扱う動作である。元の人物検出器を強くした変更ではない。

## 最終確認用の版

`conservative/` が最終の保留方針を使う版。直下の `players_*` は途中の比較版で、最終版と混用しない。

- `conservative/players_048_temporal/identity_guard_review_h264.mp4`
- `conservative/players_005_temporal/identity_guard_review_h264.mp4`
- `conservative/players_002_temporal/identity_guard_review_h264.mp4`

048では従来出していた長い欠落後の再取得IDを採用しない。
有効なF1/F2ラベルが減ることを、検出や本人同定の精度悪化と同一視しない。
逆に、灰色F?を含めて枠が増えても4人の本人同定精度とは数えない。

初期化後の元ID自体の取り違えや、短い接続の誤りまでなくなったとは主張しない。
今後の本人再識別には、同じ服の相方との混同を評価しながら、前後の軌跡や
より識別力のある外観情報を利用する必要がある。

## 検証・記録

- `test_identity_guard.py`：相方が追跡中でも比較すること、曖昧な引き継ぎの拒否、状態の復元、初期特徴の固定。
- `test_pair_policy.py`：局所的な服特徴の差があっても、似たペアの長い欠落後は保留すること。
- `audit_conservative.py`：全出力が実検出枠の座標と一致、F?に本人IDが付かないこと、
  一対一割り当て、似たペアを長い欠落後に自動復帰していないこと、コードハッシュ、
  3本のH.264/yuv420p動画の全フレームデコード。

上記は全て合格。結果は `conservative/integrity_checks.json`。
検査合格は実映像でのID精度の保証ではない。
`conservative/experiment_protocol.json` と各動画フォルダの `guard_events.json` に判断条件を保存した。
既存実験を上書きしないため、実行スクリプトは新規出力先での実行を前提とする。
