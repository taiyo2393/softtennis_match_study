# プレー区分付き・候補競合の評価専用4場面

## 目的と現状

元のvalidation120件には複数候補の競合が4フレームしかなく、3つのスコア選択規則の出力も従来と全て一致した。この問題を調べるため、学習に使わない新しい対象を4クリップから各1フレーム用意した。4件すべてユーザーがプレー中と確認し、可視の球中心をクリックした。元の300件・前回の学習用4件・選手/球/統合版の正規参照先は保持した。

今回はラリー全体の正確な開始・終端フレームの注釈を求めない。対象時点がプレー中かを人が確認し、プレー中なら球中心又は可視性を記録する。準備中・プレー後・場面が不明の場合は中心入力を省略でき、誤検出や球不在の負例へ変換しない。

## 既存情報と抽出範囲

固定validation側の012・015・019・020には、旧`manual_valid_serve_impact`かつ`impact_confirmed`の時刻がある。開始手掛かりとして再利用し、サーブ時刻から1秒後～クリップ終端1秒前だけで元モデルを推論した。カメラ退出をポイント終了と見なさず、この範囲を確定した主プレー区間とも呼ばない。

044には有効な第2サーブ・最初のフォルト・アウト終端の人手確認があるが、接触や終端の区間は引き続きAIによる暫定値。044や過去の確認済み候補が含まれるauditクリップから新しい選択用ラベルを集めず、固定した役割を保持した。得点側の確認済み回答を、イベント境界や球中心の確認へ流用しない。

## 抽出設計の変更記録

`mining_protocol.json`は最初の推論前の条件。4クリップ計716フレームをstride2で推論した。空間的競合26フレーム、面積と最大値の選択が異なるもの4フレームが見つかったが、旧注釈±8フレームを除いて3観測連続を要求すると該当区間がなかった。元スクリプトは対象0件で停止し、注釈や架空の候補は作成していない。`initial_sampling_outcome.json`へ結果を記録した。

このため、**新しい正解を取得する前に抽出設計のみ**を変更し、`sampling_revision_protocol.json`に保存した。モデル・閾値・候補選択スコアは変更しない。各クリップで面積と最大値の選択が分かれる瞬間を優先し、距離が大きいもの、同点なら早い時刻を選ぶ。該当しないクリップは複数候補の空間距離が大きいものを対照として残す。旧注釈中心から4フレーム以上離れ、t−3..tの4入力画像ハッシュが旧300件のいずれの入力とも一致しないことを検査した。カメラ切替除外は維持する。

| 場面 | クリップ/対象フレーム | ラリー候補 | 抽出の役割 |
|---|---|---|---|
| A | 012/303 | 032 | 規則で選択が分かれる |
| B | 015/328 | 040 | 規則で選択が分かれる |
| C | 019/305 | 058 | 規則で選択が分かれる |
| D | 020/171 | 063 | 複数候補があるが選択は一致する対照 |

元の注釈から4～6フレームしか離れていない対象もあり、時系列的な独立性はない。全て同一試合・既存validationクリップ内で、方式の違いを調べるために選んだ難例。代表的なランダム標本や未見試合の評価と扱わない。教師との近さを候補の順位付けへ使ってはいない。

## 推定点を隠した入力

元重み・閾値0.3でbbox_area、component_peak、bbox_mean、component_meanの16予測を回答前に`frozen_method_predictions.csv`へ固定した。予測のハッシュは`annotation_manifest.json`に保存し、入力ページ/API/動画では推定点と抽出の役割を隠す。追加学習用データへの移動は禁止する。

`serve_ball_phase_challenge.py`が127.0.0.1だけで動作し、現在のURLは`annotation_server_state.json`に記録する。画面の手順は次の3つ。

1. 全クリップの通常速度動画で、黄色枠の対象時点を見る。
2. 対象時点のプレー区分を選ぶ。開始/終了の正確なフレーム番号は不要。
3. プレー中の場合だけ、元1920×1080の対象画像で中心をクリックするか、球の可視性を選んで保存する。

プレー区分は必須。`play`と`preparation_or_ended`は明示的な人手回答、`uncertain`は人手が判断困難と回答した状態として区別する。非プレー/場面不明で中心を省略した行は`ball_annotation_scope=skipped_nonplay_or_phase_uncertain`であり、球が見えないという正解にはならない。保存は新規4件専用CSVと変更履歴だけへ行う。

4動画は元59.94fpsの2フレームごとを29.97fpsで表示する通常速度。対象で表示上約1秒停止する。合計1110表示フレームを全て復号検査済み。映像部分は1280×720で縦横比を保ち、80pxの説明欄を加えて1280×800にした。無音。動画の対象フレームとクリック画像は同じ元JPEGを使う。

## 評価と検証

### 入力後の結果

保存履歴の最終状態とCSV、対象画像ハッシュ、元フレーム時計、回答前の16予測の固定ハッシュを確認した。全4件が`human_confirmed`の`play`かつ`visible`であり、除外0件。これは4対象時点の確認であり、ラリー全体の厳密な境界確定ではない。

| 場面 | 従来の面積選択 | 最大値/矩形平均/成分平均の選択 |
|---|---|---|
| A | 正解（誤差1.41px） | 誤位置（573.17px） |
| B | 誤位置（265.63px） | 正解（1.00px） |
| C | 誤位置（222.27px） | 正解（3.00px） |
| D | 正解（1.00px） | 正解（1.00px） |

16px基準の正解数は従来2/4、スコア3方式はいずれも3/4。B/Cを回復する一方、従来正しかったAを約573px離れた位置へ移す。平均位置誤差も122.58→144.54pxと悪化するため、正解数の増加だけを改善の根拠にせず、正規版は元方式を保持した。元の正解を失う反例が得られており、auditを使って代替方式を選ぶ追加の比較は実施していない。

4件全て可視球であり、球が見えない場面の誤出力はこの比較では評価できない。また、能動的に選んだ同一試合内の4フレームの結果を、試合全体の追跡精度や時間方向の安定性として扱わない。既存120件とも合算していない。

`evaluation_report.json`が固定方式の比較、`reviewed_case_comparison.csv`が各座標と誤差、`post_review_decision.json`が元方式保持の根拠。4件を学習へ移さず、回答後にスコアや閾値を変更していない。次に時系列の候補選択を設計する場合は学習側クリップを使い、評価側のAを直すための個別ルールを追加しない。

`evaluate_ball_phase_challenge.py --status`は未入力件数のみ確認する。入力後の実行では保存履歴との一致・固定予測ハッシュ・保護入力を検査し、人手で`play`と確認され、可視性/中心が使える行だけを16px基準で比較する。非プレーや判断困難は除外理由付きで残す。元120件に機械的に合算せず、小さな選択難例での成績として分けて報告する。新しい回答でスコアの重みや閾値を調整する処理、自動的に正規版を置き換える処理はない。

保存処理は合成行のみで範囲外・非有限座標・不明ID・プレー区分未指定の拒否、非プレーの中心省略を検査した。HTTPでは4画像の元ハッシュ、4動画のRange応答、推定点がAPIに出ないこと、プレー区分未指定の400応答、注釈/履歴/固定予測がテストで変わらないことを確認した。アプリ内ブラウザでもページと最初の動画の読み込みを確認済み。

`http_verification.json`、`annotation_manifest.json`、`selected_query_frames.csv`、`query_model_inputs.csv`を検証記録とする。
