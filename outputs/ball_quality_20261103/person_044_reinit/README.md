## 問題と変更

旧`full_rally_044/bytetrack_four_player_reconnection.csv`では、far_frontはsource114864、far_rearは115216で終わり、有効サービス後115374–115775に奥2人の選択がなかった。
元の`bytetrack.csv`には、その後も奥2人に相当する検出枠が残っている。
初期IDだけを固定して追う代わりに、サービス接触候補直前source115360（local725）から再初期化した。

- 初期サーバーをF1（紫、far_rear、raw422）、パートナーをF2（黄、far_front、raw20）とする候補初期化。front/rearは初期の役割名で、移動後に名前を入れ替えない。
- 直前21フレームの近傍枠から外観の参考を取る。位置と服装に基づく候補で、人手の本人正解ではない。
- 既存の`tracking_quality_20261102_stage10/gap_pair_tracking.py`の2人同時ビーム探索をそのまま利用。探索条件、連続検出区間の所有制約、短い欠落の接続条件は変更していない。
- 奥の選手が画面右へ走る場面も候補に入るよう、粗い横方向範囲は画幅比0.20–0.90。外観・近い手前選手との重なりで別人候補を除く。服装の特徴は色ヒストグラムであり、学習済みの人物ReIDではない。
- 手前はraw2をN1、raw1をN2として元の同時刻の検出を再利用。旧選択表が打ち切られた末尾も、検出のある時刻だけ使う。
- 予測位置や補間枠を出力しない。モデルを再学習せず、既存の検出から経路を選び直している。

未来のフレームを含む区間全体を見て経路を選ぶオフライン方式。オンラインでの再取得精度とは主張しない。
