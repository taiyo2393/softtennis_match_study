# match2：選手追跡と打球確認シート

## 目的

match2の第7〜11点を対象に、「選手の自動追跡＋シートを見たClaudeによる打球ラベル」で打球単位の戦術データを作る。Aで4人の位置候補を出し、Bで打球の瞬間と打者を読むためのコマ画像シートを作る。さらに奥の拡大シート、既存ラベル、打球単位の表までをつなぐ。ボールの検出・追跡は行わない。

A・B・拡大シートの処理時間を点ごとに記録する。11/20に指導教員へ、5点の結果から全66点へ広げた場合の自動処理時間・打球数・シート数の単純外挿と、既知の失敗例を数字で示す。人のシート確認・ラベル記入・修正時間は未測定であり、今回のスクリプトだけでは人の作業時間や戦術データの正確さは評価できない。

## ファイル

| ファイル | 内容 |
| --- | --- |
| `track_points.py` | A：既存のGPU選手追跡関数を点ごとに呼ぶ。時間・位置の出力率を集計する |
| `make_review_sheets.py` | B：追跡結果を目印にした画像シートを作る。GPU不要 |

### Aの集計と時間

`tracking/timing.csv`の列：`point, first_frame, last_frame, frames, seconds, frames_per_second`。

点ごとの`track_players(...)`の直前・直後を`time.perf_counter()`で測る。`seconds`はモデル初期化・動画読込・推論・既存関数内のファイル保存を含む経過時間で、GPU推論だけの速度ではない。ラッパー側のimport・事後集計・時間CSVの保存は含まない。初回の依存モジュール初期化などで、初回と後続点の条件が異なる可能性がある。`frames_per_second = frames / seconds`。

`tracking/summary.csv`の列と定義：

| 列 | 定義 |
| --- | --- |
| `point` | 点番号 |
| `first_frame`, `last_frame` | 対象区間の両端 |
| `interval_frames` | 対象区間の全フレーム数 |
| `camera_line_supported_frames` | `camera_line_supported=1`のフレーム数 |
| `four_player_frames` | 上記のうち`assigned_slots=4`のフレーム数 |
| `four_player_ratio` | `four_player_frames / camera_line_supported_frames`。0〜1、分母ゼロは空欄 |
| `three_or_fewer_player_frames` | 線が取れた区間で`assigned_slots<=3`のフレーム数。0人も含む |

フレームの欠落・重複、点番号や区間の不一致を検査する。スキップした点に古い区間の出力が残っていれば、`--force`で作り直す。

### Bの区間とシート

`camera_line_supported=1`がフレーム番号として連続する区間のうち、長さ120フレーム以上をすべて抽出する。点ごとに時刻順に`rally_1`, `rally_2`, …と呼ぶ。この名前は**ラリー候補区間**を表し、本当のラリーかどうかは人が決める。線の取得が1フレームでも途切れれば別区間になる。

各区間の先頭から6フレームごとに採り、左から右、上から下へ3列×4行の12コマを並べる。1枚はおよそ1.2秒分で、末尾が12コマ未満の場合も同じ大きさのシートにして余りを空ける。

各コマは左右160px・上250px・下40pxを切り落として幅520pxに縮小する。調整する場合はBの`CROP_LEFT`, `CROP_RIGHT`, `CROP_TOP`, `CROP_BOTTOM`を変更する。`FRAME_STRIDE`、`MIN_RALLY_FRAMES`等も先頭の定数にまとめてある。

箱の下端中央に小さな印と短いslot名を付ける。名前とRGBは`build_044_spatiotemporal_pilot.py`に合わせている。

| slot | 表示名 | RGB |
| --- | --- | --- |
| `near_front` | N1 | (65, 220, 120) |
| `near_rear` | N2 | (70, 170, 255) |
| `far_rear` | F1 | (220, 90, 230) |
| `far_front` | F2 | (250, 210, 65) |

左上は`F{元動画フレーム番号}`、右上は位置がある人数。切り抜きの外側の印は描かないため、表示された印の数が右上の人数より少ない場合がある。JPEG品質は85。

点ごとに動画を一度開き、最初の候補区間の先頭だけシークする。その後は候補区間をまたぐ場合も`grab()`で順に進み、採用フレームだけ`retrieve()`する。`CAP_PROP_POS_FRAMES`で位置をassertし、シークを繰り返さない。

`review/point_XX/index.csv`の列：`rally, sheet, first_frame, last_frame, frames_in_sheet`。`rally`は候補区間番号、`sheet`はJPEGファイル名。両端はそのシートに実際に採った元動画フレーム番号。

`review/sheets_summary.csv`の列：

| 列 | 定義 |
| --- | --- |
| `point` | 点番号 |
| `rally_intervals` | 採用した候補区間数 |
| `rally_frames` | 候補区間の全長の合計（サンプル前） |
| `rally_seconds` | 上記を元動画FPSで割った秒数 |
| `rally_lengths_frames` | `rally_1`から順に各候補区間のフレーム長を`;`区切りで格納 |
| `sheets` | シート枚数 |
| `sampled_frames` | シートに採ったコマ数 |

`review/timing.csv`の列：`point, seconds, rally_intervals, sheets, sampled_frames`。点別入力の読込から区間抽出、動画処理、JPEG・index・summaryの保存までの経過時間。フォント読込とtiming.csv自体の保存は含まない。候補区間がなくても、ヘッダーのみのindexと0区間の集計行を出す。

A・Bとも、対象点を絞って再実行しても、全体CSV内の他点の行は保持する。再実行した点の時間は最新の値に置き換えるため、複数回の比較を行う場合は各回のCSVを別途退避する。

## 表の結合・集計規則

- 第7〜10点は第1ゲームで手前=F（船水・上松）、奥=U（内本・内田）。第11点は第2ゲームで手前=U、奥=F。第7点末尾・第8点末尾・第11点先頭のnoteと、第4〜6点の既存表の`point_winner_side`・点一覧の勝者を根拠とし、スクリプトの定数に明記する。`hitter_side=F`のFはfar、ペアコードFは船水・上松を意味し、別の変数として扱う。
- `game`・`point_winner`は点一覧を参照。`hitter_pair`は手前/奥の対応から決め、`hitter_won_point`はそのペアが点の勝者かを示す。打球自体の成功ではない。rally Aの勝敗列も後で決まった点の文脈だけを付し、Aの得点結果としては使わない。
- slot対応はN1=`near_front`、N2=`near_rear`、F1=`far_rear`、F2=`far_front`。slotは固定の選手名ではなく、入れ替わりを自動修正しない。
- `contact_frame`がある場合、slotごとに両端を含む±3フレームで最も近い有限な座標を採用。同距離なら早いフレーム。なければ座標・ずれを空欄にし、接触F自体が空欄なら全員空欄とする。補間・外挿はしない。
- `N1_x_m/N1_y_m`〜`F2_x_m/F2_y_m`は`x_m=u×10.97`、`y_m=v×23.77`。ネットはy=11.885m。既存`outputs/shot_table_20261117/build_match2_shot_table.py`と同じ換算で、手前ベースラインがy=0、奥が23.77m。コート外座標は切り詰めない。規格寸法への換算は測量精度の保証ではない。
- 各`*_frame_offset`は採用source_frame − contact_frame。`players_available`は取得人数0〜4で、各人の採用フレームは異なり得る。同一フレームに4人そろうという意味ではない。
- `hitter_pair_lateral_m/depth_m`と`opponent_pair_lateral_m/depth_m`は該当ペアの2人のabs(x差)/abs(y差)。2人分がなければ空欄。前の表と同じ定義で、ユークリッド距離ではない。
- 第8点は`near_positions_trusted=False`、全点のfarと他点のnearはTrue。第8点のN1/N2の生の座標は監査用に残し、手前ペアに対応する打者側または相手側の指標を空欄にする。Trueは「この既知の除外規則には該当しない」という意味で、独立に正しいと検証した印ではない。その他のwrong_person・missing・swappedはラベルのまま保持し、区間の補正や追加の除外はしない。
- `point_summary.csv`の打球件数・率・tracking_issueはrally Aを除く。4人取得の率は全打球を分母とし、contact_frame欠測も分母に残す。未考慮は`players_available=4`、信頼考慮はそれにnear/far両方の信頼フラグ=Trueを要求する。
- フレーム数とフレーム単位の4人出力率は`tracking/summary.csv`の値。`player_frame_availability.csv`と照合する。自動処理秒数は3工程の`timing.csv`、利用可能シート枚数は両`index.csv`の行数。通常枚数は`sheets_summary.csv`とも照合する。
- CSVはUTF-8 BOM付き、欠測は空欄、追加の真偽値はTrue/False。割合は0〜1。JSONの未測定値はnullで、入力ハッシュと定義も記録する。READMEの結果節は同じ計算結果から毎回生成する。

## 限界と解釈

- 位置が出ることと、人物同定・座標が正しいことは別。summaryは出力率であり、追跡精度ではない。4人分が出ても、別人やID入替の可能性がある。
- 印は箱の下端中央で、独立に検証した足の接地点ではない。遮蔽・空中動作・箱のずれがあり、コート上の位置も既存の固定校正に依存する。N1等は追跡slotであり、カメラ切替をまたぐ本人の一致は保証しない。
- コート線の取得は試合カメラの代理条件。リプレイ等が残る可能性も、本当のラリーが途切れたり120フレーム未満として落ちる可能性もある。全映像からのラリー検出率は今回の集計では分からない。
- 6フレーム間隔と縮小画像では、接触の瞬間・打者・終端結果を確定できない場合がある。確定が必要な箇所は次段階で元動画を確認する。曖昧なものを確定ラベルにしない。
- Claudeの読取りは補助ラベルであり、独立した正解データではない。研究の精度評価には、追跡出力に依存しない元動画の確認・照合が別途必要。
- 点の表示区間には待機・カメラ切替等も含まれる。自動処理時間と、人によるラリー選択・打球判断・修正時間を分けて報告する。本表は配置指標を算出するが、その戦術的有効性は評価しない。
- **奥の後衛の座標が深く出る（Claudeが2026-11-18に確認、同日に解釈を訂正）。** rally Aを除く奥の位置169件のうち23件（rally Aを含めると27件）は、y が26 mを超える（奥のベースライン23.77 mの2 m以上後ろ。最大38.8 m）。すべて奥の後衛（F1 slot）。
  - 当初は「カメラのズームやパン、別カメラで固定の校正が合わなくなった」と書いたが、`scenes/` で映像を場面に区切って確かめたところ、27件はすべて俯瞰の試合カメラの連続した1場面の中だった（第7点 F22721〜23986、第11点 F32550〜33107 は Claude がシートで目視確認）。別カメラは原因ではない。第7点終盤で選手が大きく見えたのは、手前の選手がカメラの近くにいたためで、ズームではなかった。
  - 奥のベースライン付近は、画面の1画素が約0.2 m以上に当たる。箱の下端の数画素のずれが数 mになる。また、後衛はベースラインの2〜4 m後ろで打つことが多いので、26〜31 mの一部は実際の深い位置の可能性がある。37.8 m（F23706）と38.8 m（F23834）は誤りの可能性が高い。どれが正しいかは未確認。
  - 奥の前後位置は誤差が大きい前提で扱い、全点に広げる前に、コート線（奥のベースライン）の画素位置と箱の下端を照らし合わせて確かめる必要がある。
